## 1. 前后端架构与技术选型理由

### 1.1 前端（Vue 3 + SPA + Pinia + EventSource）
- Vue 3：组合式 API 便于复杂状态拆分与复用，生态成熟，适合组件化对话页面
- SPA + vue-router：对话页与历史页切换频繁，路由管理清晰，状态可保留
- Pinia：集中管理 token、会话与消息流，适配 SSE 的增量更新
- EventSource：浏览器原生支持 SSE，简化流式渲染与断线重连处理
- Fetch/Axios：统一请求拦截与刷新 token 并发控制

### 1.2 后端（Node.js + NestJS/Express + SQLite）
- Node.js：事件驱动模型适合 SSE 长连接与模型推理流式输出
- NestJS：模块化与依赖注入便于拆分 Auth/Chat/Tasks 等领域
- Express 兼容：可按复杂度渐进迁移或保持轻量服务
- SQLite：单机起步与研发效率高，适用于 MVP 与中小流量
- Prisma：数据模型与迁移一致性强，降低模型演进成本

### 1.3 模块与分层（后端）
- 模块：Auth、Characters、Versions、Conversations、Messages、Uploads、Attachments、Chat、Tasks、Summaries、Safety、Observability
- 分层：Controller 协议校验，Service 业务编排，Repository 数据访问，Provider 外部依赖
- 目标：边界清晰、可测试、可替换存储与模型供应商

## 2. 角色对话业务流程实现细节

### 2.1 角色与版本
- 角色为私有资源，归属 ownerUserId
- 版本不可变：published 只读，draft 可编辑
- 新会话默认绑定最新 published；无 published 绑定 draft

### 2.2 建会话与对话
- 客户端创建会话：POST /api/conversations
- 发送用户消息：POST /api/chat/tasks（携带 clientMessageId 幂等）
- 任务创建即落库：生成 userMessage 与 assistantMessage（generating）+ generation_task（pending）
- SSE 拉流：meta → delta → done/error
- 完成落库：done 时写入 assistant 内容与 tokenUsage

### 2.3 Stop / Retry / Continue
- Stop：取消任务，assistant 标记 partial=true
- Retry：新增 assistant 消息，旧消息 supersededBy
- Continue：同一 assistant 消息续写，创建新 task

## 3. 流式传输实现原理

### 3.1 SSE 事件模型
- meta：返回 taskId、assistantMessageId、model、resumed
- delta：增量文本片段
- done：结束并携带 tokenUsage
- error：错误码与 traceId

### 3.2 断线重连
- 支持 Last-Event-ID 或 query lastEventId
- 重连后补齐当前已生成全文并继续追加
- 前端以 assistantMessageId 去重覆盖

### 3.3 连接管理
- 心跳 keepalive：每 30 秒
- 超时断开：60 秒无数据关闭
- 每用户并发连接上限：3

## 4. 图片上传实现原理

### 4.1 上传路径
- 直收 multipart：POST /api/uploads/images
- 可选直传：返回 uploadUrl 后 PUT 上传对象存储

### 4.2 扫描与状态
- scanStatus：pending / passed / rejected / failed
- rejected 不参与模型理解，仅历史展示
- 扫描引擎可选：NSFW、ClamAV、云服务

### 4.3 回放与展示
- viewUrl 仅在 passed 时返回
- viewUrl 短期有效（1 小时）
- uploadUrl 短期有效（5 分钟）

## 5. AI 使用案例与心得

### 5.1 使用案例
- 角色设定：定义背景故事、性格标签、说话风格、示例对话
- 多轮对话：结合摘要与最近 N 条对话避免上下文溢出
- 图文分析：上传图片后由模型基于 passed 附件进行理解
- 续写与重试：继续同一回复或替换为新版本输出

### 5.2 实践心得
- 先固定 Prompt 结构，再调参；避免频繁改动角色版本
- 关键链路启用幂等与限流，避免重复请求导致模型资源浪费
- 大量对话场景先做摘要，显著降低 token 消耗
- 设计错误码与提示文案，降低用户对流式中断的困惑
